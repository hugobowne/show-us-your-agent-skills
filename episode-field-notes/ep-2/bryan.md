# Bryan Bischof — Episode 2 proposals

Bryan Bischof leads AI at Theory Ventures. Per Hugo's intro he was most recently head of AI at Hex (leading the engineering team behind their data science and analytics co-pilot), started the data team at Blue Bottle Coffee, led projects at Stitch Fix, and built data teams at Weights and Biases. He co-authored an O'Reilly book on building production recommender systems and teaches data science and analytics at Rutgers, with a grad-school background in non-commutative algebraic geometry. His segment centered on BBplot and BBplot-eval: a charting package designed from scratch for agent-human collaboration, paired with a separate eval repo whose failures (not Bryan's intuitions) drive every feature decision. The distinctive angle: rather than guessing what makes a "good" agent-facing API, Bryan instruments the agent's failures, generalizes them into feature requests, and ratchets versions so the package can never regress on an eval it once passed.

## Skills

### Per-repo agent skills bundle (BBplot and BBplot-eval)
The most concrete "skills" of his demo are the multiple agent skill / instruction files he maintains inside each repo to keep agents honest: run from an editable install rather than a local checkout, do not look at BBplot's code from inside BBplot-eval, how to check out repos, how to run the server, where to read documentation, and so on. The point is constraint, not capability. *"I have a lot of agent skills because I have found that otherwise the agent does not behave super well."* He treats them as guardrails so traces become publishable and behavior reproducible. [01:40:49–01:42:00]

## Workflows

### Agent-written workflow notes, reviewed by the human
Inside BBplot-eval he keeps "agents reference" files and multiple workflow files that are not authored by him: when the agent screws up, he tells it to make a note, then he reviews the note. Over time those agent-written notes become the operating manual. *"These are things that have been written by the agent because I've complained. I've said, 'No, you screwed up again. Make yourself a note,' and then I review the note. So this is the way that I'm sort of, like, trying to converge to good functionality and good behavior in addition to just the output."* [01:42:34–01:43:00]


### Eval-driven feature development by failure generalization
The core development loop. BBplot-eval ships target charts; a builder agent tries to recreate them using only BBplot's documented examples; failures are written up by the agent; Bryan generalizes those reports into feature requests (deliberately stripped of any reference to the specific failing eval), and hands them to the builder agent inside BBplot. No feature lands because Bryan thought it would be nice. *"Feature requests to BBPlot are developed by generalizing failures on specific evals. The feature requests are not allowed to mention specific evals, but everything that is built in BBPlot is not generated by me, a human. It is generated by failures at the evals."* [01:34:25–01:34:50]

### Ratcheted versioning so the package can never regress
BBplot is released as discrete versions. If a new version regresses on any eval that an earlier version passed, BBplot-eval catches the regression and routes a patch back to BBplot. The system is allowed to fail to advance, but never to slide backwards. *"We're not allowed to move forward until we have continually ratcheted. We're not always getting better, but we're never getting worse."* [01:35:18–01:35:46]

### Hard separation of code repo from eval repo (no code-peeking)
BBplot-eval lives in a separate repo with BBplot pinned and external; agents working inside BBplot-eval are explicitly forbidden from reading BBplot's source. They may only read documented examples. The goal is to prevent both Bryan and the agents from inadvertently overfitting to implementation details. *"BBPlot is pinned and external. It is separated... In BBPlot Eval, you are not allowed to look at BBPlot's code. You are only allowed to look at the documented examples."* Hugo added that gitignoring is not enough since agents will read the git tree; Bryan agreed and noted the pin is what enforces it. [01:32:03–01:33:30]

### Parallel "background eval run" while another guest presents
A real-time demonstration of the workflow itself: while Tomasz presented his segment, Bryan kicked off a BBplot-eval run on two charts Hugo handed him (Robert De Niro's Rotten Tomatoes scores and a Leonardo DiCaprio age-of-partners chart), then returned at the end of the show to walk through what BBplot-eval produced on its first attempt, including which candidates were promoted and which were rejected. *"This is, this is where, uh, it got on its first attempt. Uh, we can see it says candidate V1. Um, this has not been promoted because it doesn't think that it was good enough. And so the evaluation criteria were not satisfied, so it doesn't promote this."* [02:14:32–02:17:00]

### Iterative chat-driven refinement on top of automated evals
Once the first BBplot-eval candidate failed, Bryan steered the next attempt by hand: pointing the agent at a built-in browser to view the result, opening a comparison page, and prompting *"Hey, isn't there an example in the gallery that shows the shaded regions?"* The agent agreed and went to fix it. The pattern: evals do the heavy lifting on the obvious failures; a few human nudges in chat close the remaining gap. [02:15:30–02:17:00]

### Multi-model harness pragmatism (Codex out, Cursor with Opus in)
Bryan tried to build the whole thing in Codex; it could not reliably use a local file system and broke on image rendering. He gave up and went back to Cursor, with Opus as his daily driver. The recurring practice is: switch the model or the harness when it fights you, do not invest energy adapting to a tool that fundamentally cannot do the job. *"This was a project that I was trying very hard to build purely in Codex, and what I learned is Codex is just, like, incapable of using a local file system and constantly breaks with image rendering. And so I completely gave up and went back to Cursor. But that's a story for another day. Um, here, uh, you can see I'm using Opus for my daily driver now."* [01:43:26–01:43:51]

## Tools / projects he showed

### BBplot
His new charting package, "very humbly" named after ggplot. Static charts (no reactive or animated charts in scope), specified in YAML, with six built-in themes and support for arbitrary functions (e.g. fitting polynomial lines). The gallery enumerates every feature paired with its spec and rendered image; a feature matrix is linted so any new feature without a corresponding gallery entry fails the lint. *"BBPlot has, like, a couple core foci, and that is what if all of your charts that you wanna make... you were making through a human agent conversation? What would you different- do differently? What would that stack of sort of, um, uh, stack of fundamental ideas from grammar of graphics look like in the agent era?"* Nights-and-weekends project; Bryan plans to open-source it. *"If it's not done by the end of this month, I'm gonna be annoyed."* [01:25:11–01:40:00, plus 01:44:49]

### BBplot-eval
A separate repo whose job is to evaluate what is possible with BBplot when used by a "fresh agent with little context," not by an oracle. Holds target charts (eval cards), a builder agent that attempts them, an orchestrator that dispatches prompts to other agents, and a feedback loop that converts failures into feature requests for BBplot. The eval set includes notable charts from history: O-ring temperature risk (the Challenger explosion chart), Datasaurus, and one of Du Bois's data visualizations. *"BBPlot Eval is a project that determines what is possible with BBPlot. It has a set of target charts that we hope BBPlot can make, but more importantly, we hope that agents can make with BBPlot."* [01:32:03–01:39:00]

The eval-card format is the unit of currency here: each target chart is an "eval card" carrying a prompt, requirements, and a "failure funnel" of predicted ways an agent could screw up. The failure funnel is what lets failures be generalized into BBplot feature requests rather than scored as a benchmark number. *"I recently introduced this definition of an eval card... Those have prompts. Those have failure funnels. Tha- have, those have predictions on how the agent could screw up. That is really, really essential because the goal is not to score high on a benchmark. The goal is to generate information about gaps."* [01:33:40–01:34:25]

### Scene graph (concept integrated into BBplot)
Borrowed from computer vision: a data structure describing what is on the chart, where, and how the elements relate. Bryan uses it inside BBplot so that complaints like "don't make the legend overlap the data" can be enforced programmatically rather than relying on agents' weak spatial reasoning. Multiple agents fail at layout, but a scene-graph warning is unambiguous. *"The scene graph knows what that means. Agents really struggle to understand those kind of things. Even, you know, VLMs or like multimodal, like language models struggle to do image understanding in a way that can easily defrag where the legend position is. This helps."* During the BBplot-eval reveal, the agent's chart was flagged for crowded labels: *"It knows because it's getting warnings from Scene Graph."* [01:29:08–01:30:24]

### Cursor
His primary development harness for both BBplot and BBplot-eval, after abandoning the Codex experiment. Usually runs BBplot-eval on one monitor and BBplot on the other; on stream he ran both inside Cursor's in-app browser. [01:40:00–01:40:30]

### Opus
Daily-driver model in Cursor for this project, mentioned after the Codex frustration. [01:43:46]

### Local DuckDB instance for trace storage
All BBplot-eval traces and iterations are published to a local DuckDB so that eval data accumulates and can be inspected over time. *"I do have a local DuckDB instance where it's publishing all the traces and sort of all of the iterations as we go, and sort of this is how I'm building out the eval, like, data."* [01:41:37–01:42:00]

### Codex (mentioned as unsuitable for this project)
Listed for completeness since Bryan's choice to leave it shaped the rest of the workflow. He had complained about it on Twitter shortly before recording. [01:43:26]

## Explainers

### Agents raise your level of ambition
Asked what he loves most about working with agents, Bryan named ambition rather than productivity. *"I feel like it raises my level of ambition. There are things that before I'd be like, 'Uh, I don't have... There's no way I'm gonna have time to do that,' or like, 'Oh,' like, 'This is the way I'd do it if I really had time to get it right.' And now sometimes I'm like, 'YOLO. Let's see what happens.' And then one thing leads to another and, yeah, I actually do much more ambitious things than I would've done before."* A short reflection but a useful counterweight to productivity-only framings of agent value. [01:21:27–01:21:55]

### Why context should be packaged with the content
The first of BBplot's "core beliefs," developed with Bryan's colleague Adam at Theory Ventures and part of a forthcoming blog post / philosophy piece. When you build something with an agent you give it a lot of context (visual preferences, data sources, target audience). If that context lives separately from the artifact you produced, it gets lost or stale almost immediately, and the artifact becomes non-portable. BBplot enforces co-location: the context lives inside the chart spec. *"The context should be packaged with the content. This is a concept that I've been working on with one of my colleagues, Adam, that when you are trying to build something with agents, you are providing lots of context about what you want built, and you either often lose that context or you package it as a separate thing that kind of gets lost or forgotten. It's not packaged with the core asset or artifact, and so you have no hope that it'll stick around. What if you just force it to be in the same place?"* [01:26:40–01:27:18]

### Ambiguity yields variance: the Midjourney design pattern
The second BBplot core belief. Midjourney returns four image variations per prompt; users learn which interpretation matches their vision by picking from the set. Bryan argues this is the right pattern for any generative system where the user knows some things and is still discovering others. BBplot is built on the assumption it should be generating variance constantly, not collapsing to a single "best" answer. *"You'd ask it for an image, and it would give you four, and those four would be subtly different. And often you would find one of those four that felt really aligned with your vision, and maybe one that was, like, okay, and then two that were way off. I think that's a great design pattern because when you are trying to build things, you very frequently have some things that you know and some things that you're trying to discover."* [01:27:18–01:28:07]

### Top-K with K greater than one (recommender-systems framing)
Bryan tied the variance principle back to his recommender-systems background: optimizing for "the single best answer" is often the wrong objective. *"I'm top K. K does not need to equal one. Like, you're allowed to let K equal five."* And on diversity in recommendation: *"I used to work on diversity in recommendation systems, which was precisely this idea that, like, actually, not getting the top K best... but getting the top K that spans the sort of distribution is even better."* Useful gloss for anyone designing agent UIs that today return one answer where they should return three. [01:28:27–01:28:58]

### Scene graphs solve the layout-awareness gap for agents (and VLMs)
Agents (including multimodal ones) are bad at reasoning about where elements sit on a chart and how they relate spatially. Saying "don't overlap the legend with the data" is hard for a VLM to enforce by looking at the image. A scene graph gives that reasoning to the system explicitly, so the same instruction becomes a checkable property. *"If you tell me there's an annotation for these five points on the chart, that's interesting... but it would be more interesting if I knew that they were on top of one another, because five annotations on top of one another is not super useful."* Thomas confirmed this is the same problem Randy Olson surfaced in the prior episode. [01:29:08–01:30:35]

### All features must be demonstrated, because agents are the main consumers
A design principle, not just a doc style. Bryan's claim: agents are now the dominant readers of API docs, so the best documentation format is a working spec plus a rendered image, not prose. BBplot enforces this with a linted feature matrix: a new feature without a gallery entry fails the lint. *"We live in a world where agents are gonna be the main consumers of these things. Remember, BB Plot is not for humans. BB Plot is for humans plus agents. And so what's the best way to document a chart builder? By demonstrating the features. So every single feature must be demonstrated as part of the gallery with the spec and the image."* [01:31:06–01:31:25]

### Be suspicious of anyone who claims to know what agents want
The most important and most counterintuitive core belief. Bryan refuses to design BBplot's DSL based on his own intuitions about what reads well to an agent. The only honest way to find out is to test, fail, generalize. *"The DSL should be optimized for agents. Now, this one is the most trite, but also the most important because as a human, I don't actually know what agents want. I can make some guesses. I can make some claims, but you should not believe me. If someone tells you, 'I know what agents want,' you should be immediately suspicious."* This is the philosophical foundation for the separate eval repo and the failure-driven feature pipeline. [01:31:21–01:32:00]

### Generating information about gaps, not chasing a benchmark
A sharp reframing of what evals are for. *"The goal is not to score high on a benchmark. The goal is to generate information about gaps."* Eval cards include predicted failure funnels so that when an agent fails, the failure is legible and routes cleanly into a feature request. The benchmark number itself is incidental. [01:33:40–01:34:25]

### Letting the system evolve toward what passes, rather than designing for what is good
Thomas noted that BBplot effectively steers itself through adversarial pressure. Bryan agreed and named the underlying assumption he is dropping: that designers know in advance what "good" is. He keeps one role for himself, the late backstop: looking at a finished chart and saying it looks bad. Everything else, including which features exist and how the DSL behaves, is decided by what passes evals. *"Letting it evolve where it needs to go to pass, and sort of, like, dropping the fundamental assumption that I think a lot of people still hold onto that they know what is good. Like, I don't really know what's good. What I do know is what charts would be great to be able to produce, and I can be a very, very late backstop on this chart looks bad. And so that's... Those are things I do know. Uh, and so I let the rest, uh, be up to the agents."* [01:43:55–01:44:35]

### Agent-written workflow notes will over-index on specifics
A practical correction to the "ask the agent to write the docs" pattern. Hugo flagged that when agents write workflows they hardcode file names and current-task details rather than generalizing. Bryan agreed, having felt the same pain: *"I wish I could say, like, 'I wrote down these agent instructions and they worked and everything was happy,' but that is not the case. In fact, it required an incredible number of iterations, and there's been a lot of slop."* The practical implication: review and re-edit agent-written workflow files aggressively before they become load-bearing. [01:43:00–01:43:30]

### Amish foundation-laying as an analogy for agent parallelization
Bryan interjected during Tomasz's segment on parallelization with a story about hiring an Amish crew to lay the foundation of his house. After nearly a year of slow in-house progress (three rows of blocks), the Amish crew did roughly fifteen times that amount of work in a single weekend, assembly-line style. *"The rate at which they did this terrified us, and the way that they did it was very much like, you know, like assembly line, like person throwing block to next person, putting it in place correctly instantly. Their, yeah, their mastery of working together was astounding."* The implicit transfer: orchestration and choreography beat raw speed when you have many workers. [01:50:49–01:51:30]
